# POSITION

**ICD-001.** Передача свежей GNSS-позиции трекера на сервер. `POSITION_V1` — бинарная схема версии 1 сообщения `POSITION`.

[Бинарная структура](#binary-layout) · [Идентификация](#identity-and-sequence) · [Выдача диапазонов](#range-allocation) · [Время и координаты](#measurement-time-and-coordinates) · [Погрешность](#horizontal-accuracy) · [Live-доставка](#live-доставка) · [Проверки при приёме](#udp-validation) · [Защита UDP](#udp-protection) · [Что ещё определить](#open-questions)

## Назначение и границы

`POSITION` передаёт одно GNSS-измерение от физического трекера или совместимого симулятора к серверной подсистеме приёма телеметрии. Описанная ниже структура относится к **полезному содержимому сообщения**, без накладных расходов сети, фрейминга, криптографической защиты и подтверждений доставки.

**Размер:** 20 байт (160 бит), фиксированная длина.

<a id="binary-layout"></a>

## Бинарная структура

Смещения отсчитываются от нуля с начала полезной нагрузки схемы `POSITION_V1`.

| Offset (байты) | Поле | Тип | Размер | Значение |
|---|---|---|---:|---|
| 0 | `header` | `uint8` | 1 Б | Версия формата + тип сообщения |
| 1–2 | `trackerId` | `uint16` | 2 Б | Идентификатор физического трекера |
| 3–6 | `sequence` | `uint32` | 4 Б | Глобальный для трекера порядковый номер события |
| 7–10 | `measuredAt` | `uint32` | 4 Б | Unix timestamp в секундах, UTC |
| 11–14 | `latitudeE7` | `int32` | 4 Б | Широта WGS 84 в градусах × 10⁷ |
| 15–18 | `longitudeE7` | `int32` | 4 Б | Долгота WGS 84 в градусах × 10⁷ |
| 19 | `horizontalAccuracy` | `uint8` | 1 Б | Оценка горизонтальной погрешности |
| | **Итого** | | **20 Б** | |

Все многобайтовые числовые поля `POSITION_V1` кодируются в **Big-Endian (network byte order)**: старший байт передаётся первым в последовательности байтов полезной нагрузки. Для полей длиной 1 байт endianness не применяется. В бинарных диаграммах старшие разряды располагаются **слева (MSB слева)**; при обозначении отдельных битов байта **бит 7 — старший, слева**, **бит 0 — младший, справа**. Это правило записи и нумерации битов **не задаёт физический порядок их передачи** — его определяет нижележащий интерфейс связи.

Примеры байтового кодирования: `trackerId = 0x1234` → `12 34`, `sequence = 0x01020304` → `01 02 03 04`. Состав, смещения и размер 20 байт не меняются. Полный тестовый вектор требует отдельного согласования прочих открытых деталей формата.

<a id="header-field"></a>

## Поле `header` (8 бит)

- Биты **7–4** содержат `version` — версию **формата сообщения** (4 бита).
- Биты **3–0** содержат `messageType` — тип сообщения (4 бита).
- Для `POSITION_V1`: `version = 1`, `messageType = 1`, поэтому **`header = 0x11`** (`0001 0001`).

`version` обозначает версию **бинарного протокола**, а не установленной прошивки трекера.

Это служебный заголовок протокола, а не отдельная файловая сигнатура. Наличие `header` не заменяет механизмы проверки целостности и аутентификации.

<a id="identity-and-sequence"></a>

## Идентификация и последовательность

### `trackerId`

- Постоянный логический идентификатор физического трекера в пределах этой системы.
- Двухбайтовый `uint16` представляет до 65 536 значений до учёта возможных резервов.
- `vehicleId` и история назначений `trackerId → vehicleId` хранятся на сервере и в каждом сообщении `POSITION` не передаются.

Связку TLS-идентичности и разрешённого `trackerId`, а также отзыв доступа определяет [KEY_MANAGEMENT](KEY_MANAGEMENT.md#authorization-and-revocation).

<a id="range-allocation"></a>

### Выдача диапазонов sequence

- `uint32`, монотонно возрастающий глобальный номер событий для одного `trackerId`.
- Номер не сбрасывается при перезагрузке трекера.
- Правило одного измерения и одной прикладной попытки определено в разделе [Live-доставка](#live-доставка).
- Поле `sourceEpoch` в этой версии исключено.
- `sequence` не выводится из UTC/RTC. **Сервер** авторитетно резервирует непересекающиеся диапазоны по **3600 номеров** на аутентифицированный `trackerId`, атомарно и долговременно сохраняя верхнюю границу **выданных** диапазонов до успешного TLS-ответа. Последний полученный UDP `sequence` не заменяет состояние распределителя; при откате/утрате server allocation state выдача останавливается до восстановления. Выдача согласуется между обслуживающими экземплярами сервера.
- Трекер хранит `requestId` ожидаемого запроса в RAM. При потере ответа он повторяет тот же запрос с тем же ID в рамках текущего запуска, в том числе после переподключения по TLS. Сервер атомарно сохраняет результат выдачи для пары авторизованного `trackerId` и `requestId` вместе с новой верхней границей до успешного ответа. Повтор возвращает тот же диапазон. Трекер принимает ответ на ожидаемый запрос текущего запуска и активирует диапазон один раз после проверки обеих EEPROM. Дубликат ответа не сбрасывает текущий `sequence`. После reboot трекер запрашивает новый диапазон с новым `requestId` и отбрасывает ответы предыдущего запуска.
- Запрос `RANGE_REQ` по TLS содержит `requestId`. Сервер определяет `trackerId` по [авторизованной TLS-сессии](KEY_MANAGEMENT.md#authorization-and-revocation). Успешный ответ `RANGE_RESP` содержит тот же `requestId` и включительные границы `firstSequence` и `lastSequence`. Трекер сверяет `requestId` ответа с ID ожидаемого запроса.
- Для каждого нового запроса выдачи трекер получает 16 случайных байт из штатного криптографического генератора (CSPRNG). При холодном старте трекер дожидается инициализации генератора с достаточной энтропией. При повторе запроса использует те же 16 байт, сохранённые в RAM.
- Тело `RANGE_REQ` (16 Б) содержит `requestId` в байтах 0–15. Тело `RANGE_RESP` (24 Б) содержит `requestId` в байтах 0–15, включительную нижнюю границу `firstSequence` в байтах 16–19 и включительную верхнюю границу `lastSequence` в байтах 20–23. Обе границы кодируются как `uint32` в Big-Endian. Диапазон содержит 3600 номеров.
- Сообщение в TLS-потоке состоит из кода типа фиксированной ширины и тела фиксированного для этого типа размера. `RANGE_REQ`, `RANGE_RESP` и `RANGE_ERR` имеют разные типы. Приёмник дочитывает полный код типа, по нему определяет размер тела и накапливает тело целиком перед разбором.
- MCU ведёт текущий `sequence` и `reservedUntil` в RAM, **две отдельные внешние EEPROM** хранят проверяемые копии выданного сервером диапазона. При проверке учитываются границы, поколение и контроль целостности копии. До активации нового диапазона обе записи последовательно выполняются и считываются/проверяются, сохраняя прежнее завершённое состояние. Нет физической атомарности между двумя EEPROM; **логическое переключение лишь после обеих проверок**. При частичной записи или отказе EEPROM новый диапазон не активируется.
- Очередной диапазон запрашивается заранее, пока доступны номера. Без связи в течение непрерывной работы можно создавать новые нумерованные измерения и сохранять архив, пока есть действующий или заранее выданный и проверенно записанный диапазон. После исчерпания номеров — остановка создания новых нумерованных событий до получения диапазона; уже записанные события остаются, диагностическое состояние фиксируется при возможности.
- После **любого reboot** остатки всех старых диапазонов пропускаются, независимо от состояния EEPROM. Для создания новых нумерованных позиций, включая записи локального журнала, трекер ждёт ответа сервера и активирует выданный диапазон после проверки обеих EEPROM. Старые записи архива сохраняют `sequence`.

Теоретически 2³² значений при 1 событии/с соответствуют приблизительно 136 годам последовательной нумерации. Из-за резервирования диапазонов фактическое число использованных номеров может расти быстрее, чем число переданных событий.

Получение достоверного UTC при холодном старте с недостоверным RTC определено в [KEY_MANAGEMENT](KEY_MANAGEMENT.md#time-bootstrap).

<a id="measurement-time-and-coordinates"></a>

## Время и координаты

### `measuredAt`

- `uint32` хранит секунды Unix с 1970-01-01 00:00:00 UTC.
- Время относится к **моменту GNSS-измерения**, а не отправке или получению на сервере.
- Точность числового представления — 1 секунда.
- Последний возможный момент для `uint32` Unix seconds — 2106-02-07 06:28:15 UTC.
- Трекер использует локальные часы реального времени (RTC), синхронизированные с достоверным UTC; после перезагрузки проверяет сохранность и достоверность времени. Время GNSS — основной источник синхронизации, сетевой источник — резервный. При временной недоступности внешних источников синхронизированный RTC продолжает отсчёт; допустимость его показаний определяется оценкой возможного дрейфа.
- Основное питание трекера проектируется независимым от положения зажигания; RTC обеспечивается резервным питанием для сохранения хода часов при потере основного питания.
- Если после запуска часы RTC сброшены или их UTC-время нельзя признать достоверным, трекер выполняет синхронизацию от GNSS или резервного сетевого источника. Пока достоверное время не получено, **`POSITION` не формируется и не отправляется**, даже если координаты уже доступны. Не подставлять фиктивные значения `measuredAt`; состояние ожидания синхронизации регистрировать локально для диагностики, не приписывая ему ложный абсолютный timestamp.
- Для `measuredAt` в `POSITION_V1` специальный маркер отсутствия времени не используется.

### `latitudeE7`, `longitudeE7`

- Геодезическая система координат — WGS 84.
- Используются целые числа со знаком `int32`.
- Для декодирования делить значение на 10⁷, получая градусы.
- Корректная широта лежит в диапазоне от −90 до +90 градусов, долгота — от −180 до +180 градусов.
- Разрешение кодирования не следует путать с физической точностью GNSS.

<a id="horizontal-accuracy"></a>

## Поле `horizontalAccuracy` (8 бит)

Поле хранит оценку горизонтальной погрешности от GNSS-приёмника в метрах. У поля нет фиксированной доверительной вероятности, а значение не гарантирует верхнюю границу фактической ошибки.

- **Бит 7** выбирает единицы: `0` — дециметры (0,1 м), `1` — метры (1 м).
- **Биты 6–0** содержат величину; значения `0xFE` и `0xFF` — специальные коды, а не обычные величины.
- `0x00–0x7F` декодируются как 0–12,7 м с шагом 0,1 м.
- `0x80–0xFD` декодируются как 0–125 м с шагом 1 м. При кодировании этот масштаб применяется **только для значений свыше 12,7 м**.
- `0xFE` означает **погрешность больше 125 м** (превышение представимого диапазона).
- `0xFF` означает **неизвестную или недоступную достоверную оценку погрешности**.

**Правило кодирования:** при известной неотрицательной оценке `a` в метрах:
1. Если `a ≤ 12,7`, записать `ceil(a × 10)` в дециметровом режиме (бит 7 = 0).
2. Если `12,7 < a ≤ 125`, записать `0x80 | ceil(a)` в метровом режиме (бит 7 = 1).
3. Если `a > 125`, записать `0xFE`.
4. Если достоверная оценка недоступна, записать `0xFF`.

Округление всегда **вверх** в выбранных единицах, чтобы само квантование не занижало сообщённую приёмником оценку.

| Исходная оценка | Код | Декодируемое значение |
|---|---|---|
| `5,36 м` | `0x36` | 5,4 м |
| `12,70 м` | `0x7F` | 12,7 м |
| `12,71 м` | `0x8D` | 13 м |
| `124,2 м` | `0xFD` | 125 м |
| `125,01 м` | `0xFE` | Больше 125 м |
| Неизвестна | `0xFF` | Неизвестна |

Трекер формирует `POSITION` только для нового измерения с достоверным GNSS-фиксом. Отсутствие фикса трекер записывает в [локальный журнал](POSITION_RECORD.md#purpose). Для состояния устройства предусмотрен отдельный [DEVICE_STATUS](DEVICE_STATUS.md).

## Live-доставка

Одно допустимое GNSS-измерение → один заранее зарезервированный `sequence` → одно неизменное 20-байтное логическое сообщение → **один вызов AES-128-CCM-8 с nonce `prefix[8] || sequence[4]`** → **одна прикладная попытка отправить готовую 28-байтную UDP-датаграмму**. После передачи в интерфейс модема/UDP новое шифрование, переупаковка и прикладная повторная отправка этого live-события запрещены, включая случаи неопределённого результата отправки или ошибки модема. `sequence` никогда не переиспользуется для нового измерения либо исправления уже сформированных координат/времени. Ретрансляции нижележащей сотовой/IP-сети, неподконтрольные прикладному уровню, не являются повторным шифрованием приложением.

При отказе/неопределённом результате отправки фиксируется состояние через локальный журнал и [`SEND_STATUS_V1`](POSITION_RECORD.md#send_status_v1); пропущенные события восстанавливаются только через `ARCHIVE_TRANSFER` по TLS/TCP с отдельным прикладным `ARCHIVE_ACK` после durable-save. Сервер независимо от этой политики отклоняет криптографические/логические дубликаты при помощи anti-replay. Политика не распространяется на идемпотентные повторы **сервисных** TLS-команд (например, `REKEY_REQ`).

- Транспорт для `POSITION` — **UDP**. При номинальном 1 Гц валидное свежее измерение передаётся с наивысшим приоритетом, без ожидания старых событий, локальной записи или отчётов. Live-профиль допускает отдельные пропуски и обходится без прикладного ACK или повторной отправки.
- В `POSITION_V1` отсутствуют поля `sendDelta` и `flags`. Время и результат локальной отправки описывает [локальная запись](POSITION_RECORD.md).
- При приёме проверяются формат, источник, достоверность и уникальность события. Непредвиденный сетевой дубликат того же события не применяется повторно. Тот же ключ с другим payload — наблюдаемый конфликт идентичности. Повреждённые данные и нарушения аутентификации обрабатываются отдельно от обычных пропусков.
- Пропуск номера после [серверной выдачи](#range-allocation) не доказывает потерю события.
- Цели свежести и задержки задаёт [SRS](SRS.md#freshness-and-latency). Подтверждение устойчивого приёма относится к [архиву](ARCHIVE_TRANSFER.md#ack-and-resume).

<a id="live-publication"></a>

### Публикация на сервере

Сервер публикует позицию трекера только если успешно аутентифицированное и прошедшее anti-replay сообщение имеет `sequence > lastPublishedSequence` для **этого trackerId**. `lastPublishedSequence` — логическое состояние публикации, оно **не сбрасывается при ротации AES-ключа**. Пакеты, поступившие не по порядку (например, 102 раньше 101), могут обрабатываться для необходимых независимых статистик, но старый `sequence` **не изменяет live-позицию**. Обновление последнего опубликованного номера и позиции должно быть согласованным, чтобы параллельные обработчики не публиковали старый пакет поверх нового.

Если новые позиции не поступают, клиент помечает последнюю известную координату как **устаревшую**. Поля `assignmentVersion` и `vehicleId` отсутствуют в UDP-пакете. Административное назначение `trackerId → vehicleId` хранится на сервере, сложное версионирование переназначений за пределами MVP. [FR-036 для MVP](DECISIONS.md#open-questions) · [Требования к порядку](SRS.md#44-data-processing--state-semantics)

<a id="udp-validation"></a>

## Проверки при приёме UDP

Злоумышленник или неисправная сеть может направлять на публичный UDP-порт множество пакетов с чужим или несуществующим `trackerId`. До затратной криптографии сервер выполняет ограниченные по стоимости, не требующие доверия к пакету проверки:

1. Проверить **точную длину UDP payload = 28 Б** для согласованной схемы `POSITION_V1` и поддерживаемое значение заголовка `0x11`. Некорректный размер/тип/версия — отклонить до вызова AES-CCM.
2. Прочитать открытый `trackerId` только как **недоверенное указание на серверный контекст**: если активного разрешённого контекста нет (или он заблокирован), пакет отклонить без CCM. Это **не авторизация** отправителя, так как подлинность `trackerId` ещё не проверена тегом.
3. Применять **ограничение ресурсов до криптографии** (bounded queue/нагрузка, контроль частоты недействительных попыток, бюджет криптопроверок), предотвращая неограниченный расход CPU и памяти. Не считать IP-адрес или открытый `trackerId` достоверным признаком отправителя; меры против перегрузки не должны позволять легко надолго заблокировать добросовестный трекер только подделкой его `trackerId`.
4. Проверить AES-CCM-тег допустимой эпохи. В обычном состоянии — **одна** допустимая эпоха; в согласованном переходе — максимум **две** (`K_new` первой, `K_old` только после неверного тега), по правилам смены ключа. Только после успешного тега проводить anti-replay и дальнейшую валидацию/публикацию.
5. Собирать агрегированную диагностику отброшенных пакетов и перегрузки с ограниченными накладными расходами; диагностическая нагрузка не должна стать самостоятельным источником DoS.

Отказ из-за превышения лимита не подтверждает отказ устройства. Проверки выполняются на существующей 28-байтной UDP-датаграмме.

<a id="udp-protection"></a>

## Защита UDP

Для live-сообщения `POSITION` используется **AES-128-CCM с 8-байтным тегом** и **16-байтным ключом**. [Основания выбора](DECISIONS.md#udp-crypto-decision)

- Строго **7 Б незашифрованного, но аутентифицированного AAD** (`header`, `trackerId`, `sequence`), **13 Б ciphertext** (`measuredAt`, `latitudeE7`, `longitudeE7`, `horizontalAccuracy`) и **8 Б AES-CCM authentication tag**. Размер UDP payload для этого профиля: **28 Б**. Все исходные поля и их кодирование сохраняются, меняется лишь их представление в передаваемом сообщении. Сервер читает AAD, определяет трекер и допустимую ключевую эпоху, восстанавливает nonce по `sequence` и проверяет CCM-tag до принятия данных. Все 7 Б AAD защищены тегом от незаметной модификации, хотя доступны наблюдателю.
- **Побайтовая структура UDP payload**

  | Смещение, байты | Длина | Содержимое | Криптографический режим |
  |---|---:|---|---|
  | 0 | 1 | `header = 0x11` | AAD, открыто |
  | 1–2 | 2 | `trackerId:uint16` | AAD, открыто |
  | 3–6 | 4 | `sequence:uint32` | AAD, открыто |
  | 7–10 | 4 | `measuredAt:uint32` | AES-CCM ciphertext |
  | 11–14 | 4 | `latitudeE7:int32` | AES-CCM ciphertext |
  | 15–18 | 4 | `longitudeE7:int32` | AES-CCM ciphertext |
  | 19 | 1 | `horizontalAccuracy:uint8` | AES-CCM ciphertext |
  | 20–27 | 8 | `CCM tag` | Authentication tag |

  `trackerId` и `sequence` в AAD кодируются в Big-Endian. Шифротекст составляется из байтов 7–19 исходного 20-байтного payload до шифрования. AAD — байты 0–6; тег относится и к AAD, и к ciphertext.
- 12-байтный nonce для AES-CCM-8: `nonce = prefix[8] || sequence[4]`. В пределах одной эпохи рабочего AES-ключа `prefix` фиксирован. Он выводится через [TLS Exporter](KEY_MANAGEMENT.md#tls-exporter). `sequence` — глобальный `uint32` из схемы `POSITION_V1` в Big-Endian. Для данного ключа никакое значение `sequence` не используется повторно. Трекер и сервер восстанавливают nonce **без отправки его в каждом UDP-пакете**; хранить перечень всех использованных nonce на сервере не нужно.
- После успешной проверки тега применяется [защита от повторной обработки](KEY_MANAGEMENT.md#replay-state-recovery) для выбранной ключевой эпохи.
- Смена ключа и запрет перехода на открытый UDP определены в [контракте rekey](KEY_MANAGEMENT.md#rekey).
- Порядок проверок ключевых контекстов задан в [KEY_MANAGEMENT](KEY_MANAGEMENT.md#udp-key-selection). Поле `keyId` в датаграмме отсутствует.

Установление ключей, протокол rekey и обработка потери `REKEY_RESP` описаны в [KEY_MANAGEMENT](KEY_MANAGEMENT.md#rekey). Там же определены [срок ключа и периодическая TLS-сверка](KEY_MANAGEMENT.md#key-expiry-and-reconciliation) и [профиль TLS Exporter](KEY_MANAGEMENT.md#tls-exporter).
