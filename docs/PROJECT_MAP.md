# PROJECT MAP — Transport Telemetry

**Срез 2026-11-09.** [Master ICD](icd/README.md) ведёт к текущим контрактам. [PROJECT_CONTEXT](PROJECT_CONTEXT.md) хранит историю и основания решений.

## Цель

Собственная система GNSS-мониторинга общественного транспорта. MVP — один трекер, сервер, карта и симулятор. Целевые масштабы из SRS — около 5 000 трекеров и 10 000 клиентов. В номинальном режиме поступает одна координата в секунду.

## Принципы проектирования

[Философия проекта](PROJECT_PHILOSOPHY.md) — не выдавать неопределённость за достоверность; гарантировать проверяемые инварианты в заданной модели отказов, а не безошибочность внешней среды. [Исследовательский backlog](RESEARCH_BACKLOG.md) — отказоустойчивые распределённые системы и возможный ИИ-прогноз времени прибытия автобусов **после MVP**, без утверждения новых протоколов или функциональных требований.

## Потоки

```text
GNSS → tracker → POSITION_V1 (20 Б, UDP) → live backend → текущее состояние → карта
           └──→ POSITION_LOG_RECORD_V1 (~35 Б) → NVM → ARCHIVE_TRANSFER (TCP) → архив
tracker → TX_SUMMARY (60 с) → сервер
tracker ← RX_SUMMARY (60 с) ← сервер, независимо от TX
управление и OTA ↔ защищённый подтверждаемый обмен (полный контракт OPEN)
```

Свежая позиция имеет приоритет. **APPROVED R6:** live backend публикует только `sequence > lastPublishedSequence` для trackerId независимо от key epoch, а при молчании трекера интерфейс помечает координату устаревшей (порог OPEN); сложное переназначение не требуется для MVP. **APPROVED R4:** один live `sequence` шифруется ровно один раз и передаётся одной прикладной UDP-попыткой без повторов; пропущенные события доступны через архив. `(trackerId, sequence)` связывает представления одного события, а назначение трекера автобусу ведёт сервер. Время измерения, локальной отправки и серверного приёма различаются. История может иметь пропуски, её выгрузка не меняет текущее состояние и live RX.

## Приём недостоверного UDP

**APPROVED (P1 R9):** перед проверкой AES-CCM — дешёвые проверки ровно 28 Б, `header=0x11`, наличие разрешённого контекста для заявленного `trackerId` и лимит ресурсов приёмника. Отправитель ещё не удостоверен до тега: поддельный ID не должен автоматически лишать настоящий трекер доступа. Численные лимиты **OPEN**. [Порядок обработки](icd/POSITION_V1.md#r9--предварительные-проверки-и-ограничение-ресурса-udp-приёмника).

## Ключи и защищённая среда

**APPROVED (P1 R8):** сервер связывает TLS-удостоверенную идентичность устройства с конкретным разрешённым `trackerId` и прекращает приём всех его UDP-эпох и TLS-операций при блокировке. Provisioning и распределённый отзыв — OPEN. [KEY_MANAGEMENT](security/KEY_MANAGEMENT.md#авторизация-trackerid-и-отзыв-доступа).

**APPROVED (архитектура):** [KEY_MANAGEMENT](security/KEY_MANAGEMENT.md) — индивидуальный долгосрочный приватный ключ в защищённой области MCU либо Secure Element; временный AES-CCM-8-ключ только в RAM, TLS 1.3/ECDHE для установления и недельной ротации по отдельному сервисному запросу трекера, новый ключ после reboot, без открытого fallback. Временная поддержка двух ключевых эпох и логический обмен `REKEY_REQUEST → REKEY_ACK` при rekey **APPROVED**; первый успешно проверенный UDP новой эпохи неявно подтверждает переход. Логические `requestId/currentEpoch/newEpoch` и сверка после TLS reconnect **APPROVED**; бинарные размеры/коды и timeout/overlap **OPEN**. Противодействие физическому доступу — требование, реализация и threat model OPEN.
