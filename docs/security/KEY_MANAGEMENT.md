# KEY_MANAGEMENT — защита секретов и жизненный цикл ключей

**Статус: APPROVED (2026-11-10) — архитектурные принципы.** Требование: защищаться от сетевой подделки, перехвата и практически реализуемого физического чтения секретов с устройства. Это **не означает гарантированную абсолютную защиту** от любого физического вмешательства; конкретная модель угроз, tamper resistance и проверки реализации **OPEN**.

## Хранение и назначение ключей

- **APPROVED:** каждый трекер имеет **собственную долгосрочную асимметричную криптографическую идентичность**. Неэкспортируемый приватный ключ хранится в защищённой аппаратной среде: встроенная защищённая область подходящего MCU **либо** отдельный Secure Element. Конкретный чип, интерфейс, сертификаты и provisioning **OPEN**.
- **APPROVED:** обычная внешняя EEPROM хранит `sequence`, его журнал резервирования и несекретное служебное состояние. **Долгосрочный приватный ключ и рабочие симметричные ключи не сохраняются в открыто читаемой EEPROM**.
- **APPROVED:** временный симметричный ключ для `POSITION_V1` существует в RAM на время применения. Ключ не сериализуется вместе с UDP-сообщением и не попадает в логи. После перезагрузки/утраты RAM рабочий ключ **создаётся заново** через аутентифицированный обмен.

## Установление и обновление ключей

- **APPROVED (принцип):** использовать защищённое аутентифицированное соединение на базе **TLS 1.3 с проверкой устройства и сервера**, включая ECDHE для установления общего секрета. Из согласованного контекста выводится **отдельный ключ AES-CCM-8 для live UDP**, например стандартным TLS Exporter (конкретная привязка контекста и поддержка экспортера **OPEN**). Долгосрочные приватные ключи не пересылаются; TLS/ECDHE не выполняется для каждого UDP-пакета.
- **APPROVED:** **плановая ротация рабочего ключа приблизительно раз в неделю**, плюс обновление после перезагрузки/потери состояния и при необходимости восстановления защищённой сессии. Долгосрочный идентификационный ключ **не требуется менять еженедельно**.
- **APPROVED (2026-11-10, сервисная операция):** трекер инициирует отдельный **запрос обновления UDP-ключевого контекста** по защищённому TLS 1.3-каналу, включая плановую еженедельную ротацию. Для нового контекста выполняется **новый взаимно аутентифицированный TLS 1.3/ECDHE-обмен** и выводится новый симметричный ключ AES-CCM-8 и связанный nonce-prefix. **Приватные и готовые симметричные ключи по сети не пересылаются**. Обычное TLS 1.3 `KeyUpdate` меняет ключи самого TLS-канала и само по себе **не обновляет экспортированный ключ UDP**; требуется новый контекст вывода ключа.
- **APPROVED (принцип перехода):** трекер и сервер согласуют новую ключевую эпоху по защищённому управляющему каналу и переходят на неё без неподтверждённого отката. В краткий, строго ограниченный переходный период сервер **может проверять** допустимые старую и новую эпохи, чтобы обработать запоздавшие UDP-датаграммы; старый ключ удаляется после завершения периода. Проверка всех допустимых контекстов должна быть ограничена по времени и количеству, с anti-replay для каждого соответствующего контекста.
- **PROPOSED (имена/детали обмена):** `REKEY_REQUEST` → `REKEY_READY` → `REKEY_ACTIVATE` как возможные стадии сервисной операции, **не утверждённые** как имена бинарных команд или обязательный трёхшаговый wire-протокол. **OPEN:** сценарии отказа/повторов, тайм-ауты, подтверждение активации, переключение двух эпох без `keyId`, допустимое окно старых сообщений и обработка утраты связи на переходе.
- **APPROVED:** после reboot требуется повторная аутентификация и получение нового рабочего ключа прежде, чем продолжать шифрованный live. При невозможности установить безопасный ключ **не переходить на незашифрованный UDP** и не отправлять `POSITION_V1` без аутентификации; локальный журнал и диагностика продолжаются по допустимым режимам.
- **APPROVED:** чувствительные архивные данные и управление/OTA также должны передаваться по аутентифицированным защищённым каналам. Для `ARCHIVE_TRANSFER` через TCP выбран **TLS 1.3** как профиль защиты. Конкретные потоки управления, сертификаты, авторизация и отдельная проверка подписей OTA **OPEN**.

## Связь с POSITION_V1

- **APPROVED:** полезная нагрузка `POSITION_V1` по UDP — AES-CCM-8 с 8-байтным тегом, внутри исходные 20 Б без изменений. Целевой сетевой payload **28 Б** только при отсутствии дополнительных передаваемых полей nonce, key-id, epoch; эта экономия не должна отменять требования безопасности.
- **APPROVED (2026-11-10):** nonce AES-CCM-8 — **12 байт**, `nonce = prefix[8] || sequence[4]`. Внутри эпохи рабочего ключа 8-байтный префикс фиксирован, согласован/выведен из защищённого TLS 1.3-контекста, а 4-байтный `sequence` — существующее поле позиции (`uint32`, Big-Endian). Префикс не передаётся с каждым UDP-пакетом. Повторы nonce с тем же ключом запрещены; новая эпоха должна иметь безопасно согласованный контекст ключа и nonce.
- **APPROVED:** серверу не требуется база всех использованных nonce: он восстанавливает значение по контексту ключа/эпохи и `sequence`. После проверки CCM-тега сервер применяет защиту от повторной обработки событий (replay) с учётом перестановок UDP. При сбоях сервера необходимое replay-состояние не должно теряться незаметно. **OPEN:** конкретное окно/bitmap, его сохранение, правила обработки старой эпохи.
- **OPEN:** чтобы использовать 28 Б UDP payload, сервер должен узнать `trackerId`, `sequence` и соответствующую эпоху без отдельных передаваемых nonce/key-id. Разбиение 7 Б открытого AAD + 13 Б ciphertext остаётся **PROPOSED**; распределение полей и механизм согласования/перехода эпох **OPEN**. Нельзя принимать сообщение без успешной аутентификации как положение автобуса.

## OPEN — реализация, испытания и жизненный цикл

- Подходящий MCU с защищённым хранением vs отдельный Secure Element; реальная защита от чтения/отладки и физического компрометационного доступа, secure boot, подписанные прошивки, anti-rollback, реакция на вскрытие и восстановление после взлома.
- Provisioning личности при производстве, доверенный серверный корень, выпуск/хранение/обновление сертификатов и отзыв устройств.
- TLS 1.3 / взаимная аутентификация на конкретном модеме и TLS-стеке, TLS Exporter либо иной стандартизированный KDF, раздельные ключи и контекст приложения, защита от компрометации RAM/firmware.
- Граница недельного периода, действия при недоступности сервера во время ротации, точный сервисный формат/коды `REKEY_*` (PROPOSED), подтверждение активации, длительность совместного приема допустимых эпох, server-side epoch без обязательного увеличения UDP, получение/вывод prefix[8], конкретный anti-replay window и сохранение его состояния после сбоя.
- Защита архивов и команд на уровне полномочий, OTA подпись + версия, хранение исторических данных на сервере, тест-векторы и threat modeling.
