# Transport Telemetry — Decision Register

**Версия:** 0.1  
**Дата:** 7 ноября 2026  
**Назначение:** компактная карта согласованного, предложенного и открытого. Полные требования остаются в SRS; точные форматы — в ICD.

## Значение статусов

- **APPROVED** — согласовано как требование/принцип; не обязательно утверждён способ реализации.
- **PROPOSED** — вариант или гипотеза; запрещено трактовать как действующее требование.
- **OPEN** — вопрос для следующего решения.
- **BASELINE** — действующее требование прежнего SRS, даже если предложена конфликтующая замена.

## Решения

| ID | Тема | Статус | Суть / замечание |
|---|---|---|---|
| DEC-001 | `POSITION_V1` | APPROVED | 20 байт; header 1, ID 2, seq 4, Unix seconds 4, координаты 8, accuracy 1; точный endianness OPEN |
| DEC-002 | Identity | APPROVED | Ключ события `(trackerId, sequence)`, глобальный seq после reboot, `sourceEpoch` исключён |
| DEC-003 | Near-live priority | APPROVED | Новые координаты не ждут старые ACK и диагностику |
| DEC-004 | Мониторинг качества | APPROVED | Наблюдать потери/задержки/недоступность без исключений в live path; сбор асинхронный |
| DEC-005 | Диагностика счётчиков | APPROVED | Сопоставлять generated/sent (device) и received/committed (server), не выводить loss только из seq-gap |
| DEC-006 | History reliability | BASELINE + PROPOSED CHANGE | SRS v1.1 требует durable acceptance/replay; best-effort history предложена, но не принята |
| DEC-007 | POSITION ACK policy | OPEN | No-ACK / Solo / Batch / hybrid — сравнить без предположения о выборе |
| DEC-008 | Feedback report | PROPOSED | Периодическая сводка качества приёма, возможно без ACK; формат/частота OPEN |
| DEC-009 | Адаптивная избыточность | PROPOSED | Возможность алгоритма, не конкретное дублирование каждого шестого |
| DEC-010 | NVM sequence persistence | OPEN | FRAM/MRAM на событие vs EEPROM/Flash блоками; пример 3600 номеров |
| DEC-011 | 24-hour buffer | BASELINE + PROPOSED CHANGE | Текущая цель 24 ч в SRS; необходимость пересматривается |
| DEC-012 | Мониторинг стоянок | APPROVED (потребность) | Длительный простой — повод для анализа, не автоматически нарушение |
| DEC-013 | Ночные рейсы | APPROVED (ограничение) | Ночь != стоянка; часть автобусов работает ночью |
| DEC-014 | Mode detection | PROPOSED | Использовать фактический режим рейса/парковки, не только часы |
| DEC-015 | Питание не от зажигания | PROPOSED | Требует оценки энергопотребления и защиты бортового аккумулятора |
| DEC-016 | Backup battery | OPEN | Нужна ли физическая резервная батарея и какая автономность |
| DEC-017 | Ночное управление | OPEN | Требования к доступности OTA и remote configuration вне рейса |
| DEC-018 | Driver advisory | PROPOSED | Информационный сигнал при наличии безопасного согласованного интерфейса |
| DEC-019 | Remote management security | APPROVED (SRS v1.1) | Проверяемая конфигурация, защищённые команды и OTA сохраняют надёжность |

## Приоритетные вопросы на следующий сеанс

1. Что должен гарантировать `POSITION`: best-effort только для live, надёжный архив или гибрид?
2. Если No-ACK — нужна ли вообще обязательная передача истории после offline? Какие потери приемлемы?
3. Нужен ли обратный `RECEPTION_REPORT`, и должен ли он подтверждаться?
4. Каким способом трекер достоверно узнаёт `IN_SERVICE` / `PARKED`, учитывая ночные рейсы?
5. Нужен ли собственный backup-источник при питании от автобуса?
